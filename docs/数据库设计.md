# fitness-ai 数据库设计

> 第 2 周产出。四张核心表：`user`、`exercise`、`workout`、`workout_set`。
> 建表脚本：[`docker/init/init.sql`](../docker/init/init.sql)

---

## 一、为什么是四张表

健身训练数据天然有三层结构：

```
用户 (user)
  └── 一次训练 (workout)          ← 2026-11-02 练胸
        └── 某个动作的某一组 (workout_set)   ← 杠铃卧推 第3组 60kg × 8次
                  ↑
            动作字典 (exercise)   ← 杠铃卧推 / 杠铃深蹲 / 引体向上…
```

如果只设计一张大表，会出现两个问题：
1. **数据冗余**：同一动作名称在每次训练里重复存几十遍，改名字要改几千行。
2. **无法统计分析**：「这个动作的历史最大重量是多少」这种查询会非常难写。

拆成四张表后，动作名称只存一份（`exercise`），训练记录只存"什么时候练的"（`workout`），
最细的粒度（重量 × 次数）存在 `workout_set`。

## 二、表结构

### 1. `user` 用户表

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | BIGINT UNSIGNED PK | 主键，自增 |
| `username` | VARCHAR(50) UNIQUE | 登录用户名 |
| `email` | VARCHAR(120) UNIQUE | 邮箱，可空 |
| `password_hash` | VARCHAR(255) | **bcrypt 哈希，绝不存明文** |
| `nickname` / `gender` / `height_cm` / `weight_kg` | — | 个人资料 |
| `created_at` / `updated_at` | DATETIME | 自动维护 |

**设计要点**：
- `password_hash` 长度给到 255：bcrypt 输出固定 60 字符，但留余量方便以后换算法（如 argon2）。
- `email` 加唯一索引但允许 NULL：MySQL 的唯一索引允许多个 NULL，不冲突。

### 2. `exercise` 动作字典表

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | BIGINT UNSIGNED PK | 主键 |
| `name` | VARCHAR(80) | 动作名，如「杠铃卧推」 |
| `body_part` | VARCHAR(20) | 胸/背/腿/肩/手臂/核心/有氧，**建普通索引**（按部位筛选是高频查询） |
| `equipment` | VARCHAR(30) | 杠铃/哑铃/器械/自重/绳索 |
| `is_compound` | TINYINT(1) | 是否复合动作（深蹲、硬拉算） |
| `user_id` | BIGINT UNSIGNED NULL | **NULL = 系统预置动作；非 NULL = 用户自定义** |

**设计要点**：
- 用 `user_id IS NULL` 区分系统动作和用户自定义动作，避免再开一张表。
- 唯一索引建在 `(name, user_id)` 上：同一个用户不能有两个同名动作。（注意：因为 MySQL 唯一索引允许多个 NULL，系统动作的重名需要靠初始化脚本保证。）

### 3. `workout` 训练记录表

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | BIGINT UNSIGNED PK | 主键 |
| `user_id` | BIGINT UNSIGNED FK | 所属用户，级联删除 |
| `workout_date` | DATE | 训练日期 |
| `duration_min` | SMALLINT UNSIGNED | 训练时长（分钟） |
| `mood` | TINYINT | 感受 1-5 |
| `note` | VARCHAR(500) | 备注 |

**设计要点**：
- `UNIQUE KEY (user_id, workout_date)`：**一个用户一天只能有一条训练记录**。这条约束很重要，否则"本周训练量"统计会因为重复记录而翻倍。
- `KEY idx_user_date (user_id, workout_date)`：为「查某用户某时间段的训练」准备的**联合索引**，符合最左前缀原则。

### 4. `workout_set` 训练组表（最细粒度）

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | BIGINT UNSIGNED PK | 主键 |
| `workout_id` | BIGINT UNSIGNED FK | 所属训练，级联删除 |
| `exercise_id` | BIGINT UNSIGNED FK | 动作 |
| `set_index` | TINYINT UNSIGNED | 第几组，从 1 开始 |
| `weight_kg` | DECIMAL(6,2) | 重量（自重填 0） |
| `reps` | SMALLINT UNSIGNED | 次数 |
| `rpe` | TINYINT | 主观疲劳度 1-10 |
| `is_warmup` | TINYINT(1) | 是否热身组 |

**设计要点**：
- `UNIQUE KEY (workout_id, exercise_id, set_index)`：防止同一组被插入两次。
- 重量用 `DECIMAL` 而不是 `FLOAT`：**金额和重量这类需要精确的值绝不能用浮点数**（这是面试常考点）。
- `is_warmup` 单独标记：统计训练容量时通常要排除热身组。

## 三、核心 SQL

### 1. 某用户某次训练的所有动作与组（多表连接）

```sql
SELECT e.name           AS exercise_name,
       e.body_part,
       ws.set_index,
       ws.weight_kg,
       ws.reps,
       ws.weight_kg * ws.reps AS volume
FROM workout_set ws
         JOIN workout  w ON ws.workout_id  = w.id
         JOIN exercise e ON ws.exercise_id = e.id
WHERE w.user_id = 1
  AND w.workout_date = '2026-11-02'
  AND ws.is_warmup = 0
ORDER BY e.name, ws.set_index;
```

### 2. 每个动作的历史最大重量（聚合）

```sql
SELECT e.name                     AS exercise_name,
       MAX(ws.weight_kg)          AS personal_best,
       COUNT(*)                   AS total_sets,
       SUM(ws.weight_kg * ws.reps) AS total_volume
FROM workout_set ws
         JOIN exercise e ON ws.exercise_id = e.id
         JOIN workout  w ON ws.workout_id  = w.id
WHERE w.user_id = 1
  AND ws.is_warmup = 0
GROUP BY e.id, e.name
ORDER BY personal_best DESC;
```

### 3. 本周训练量排行榜（第 4 周会走 Redis ZSet 缓存）

```sql
SELECT w.user_id,
       u.nickname,
       SUM(ws.weight_kg * ws.reps) AS weekly_volume
FROM workout_set ws
         JOIN workout w ON ws.workout_id = w.id
         JOIN `user`  u ON w.user_id     = u.id
WHERE w.workout_date BETWEEN '2026-11-09' AND '2026-11-15'
  AND ws.is_warmup = 0
GROUP BY w.user_id, u.nickname
ORDER BY weekly_volume DESC
LIMIT 10;
```

## 四、索引优化记录（第 2 周实验）

### 实验：给 `workout` 加联合索引前后对比

```sql
-- 建索引前
EXPLAIN SELECT * FROM workout WHERE user_id = 1 AND workout_date >= '2026-11-01';
-- 预期：type = ALL（全表扫描）

-- 建联合索引
ALTER TABLE workout ADD KEY idx_user_date (user_id, workout_date);

-- 建索引后
EXPLAIN SELECT * FROM workout WHERE user_id = 1 AND workout_date >= '2026-11-01';
-- 预期：type = range，key = idx_user_date
```

### 最左前缀原则验证

```sql

SELECT * FROM workout WHERE user_id = 1;

-- 能命中索引（user_id + workout_date 都在）
SELECT * FROM workout WHERE user_id = 1 AND workout_date = '2026-11-02';

-- ⚠️ 命中不了！跳过最左列直接用 workout_date
SELECT * FROM workout WHERE workout_date = '2026-11-02';
```

## 五、常见索引失效场景（自己动手验证）

| 场景 | 例子 | 为什么失效 |
|---|---|---|
| 对索引列做运算 | `WHERE YEAR(workout_date) = 2026` | 索引存的是原始值，函数运算后无法比对 |
| 隐式类型转换 | `WHERE user_id = '1'`（user_id 是数字） | MySQL 会把列转成字符串比较 |
| 前导模糊匹配 | `WHERE name LIKE '%卧推'` | 无法确定从哪里开始匹配 |
| 违反最左前缀 | 见上方第三个 SQL | 联合索引按顺序比较 |
| OR 连接非索引列 | `WHERE user_id = 1 OR note = 'xxx'` | note 没索引，只能全表扫 |
