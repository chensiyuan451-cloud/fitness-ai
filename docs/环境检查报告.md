### ⚠️ 为什么 MySQL 用 3307 而不是 3306

本机 **Windows 服务 `MySQL80`**（数据在 `E:\MySQL\Data`，里面有你自己建的
`thesis_demo` 和 `yolo_detection` 两个库）启动类型是**自动**，重启后会自己起来并占用 **3306**。

**处理方式**：不改动那个实例（数据一条没动），让 **Docker 的 MySQL 用 3307**，两个实例并存：

| 实例 | 端口 | 用途 | 管理方式 |
|---|---|---|---|
| Windows 服务 MySQL80 | 3306 | 你已有的 `thesis_demo` / `yolo_detection` | `E:\MySQL\启动MySQL.bat` / `停止MySQL.bat` |
| **Docker 容器 fitness-mysql** | **3307** | **fitness-ai 项目** | `docker compose up -d` / `down` |

> 🔁 两个实例的**账号密码是独立的**，不要混用。
> 想彻底只用 Docker 那套，可以用管理员身份执行
> `Set-Service MySQL80 -StartupType Manual` 然后 `Stop-Service MySQL80`。

### ⚠️ 踩坑记录：MySQL 初始化时中文变乱码

第一次建库后，`exercise` 表里「腿」变成了 `è…¿`，「胸」变成了 `èƒ¸`。

**原因**：容器首次执行 `docker/init/init.sql` 时，`mysql` 客户端**没有指定字符集**，
默认按 `latin1` 解读这个 UTF-8 文件里的中文，于是把 3 字节的 UTF-8 序列当成 3 个拉丁字符存了进去。

**修复**：在 `init.sql` **开头**加两行（已提交到仓库）

```sql
SET NAMES utf8mb4;
SET CHARACTER SET utf8mb4;
```

然后**必须重建数据卷**（init.sql 只在数据卷为空时执行）：

```powershell
docker compose rm -sf mysql
docker volume rm fitness_mysql_data      # ⚠️ 会清空数据库，开发阶段无所谓
docker compose up -d mysql
```

> 💡 **这个坑面试也能用上**：面试官问「你项目里怎么处理中文乱码」，
> 你就可以从「服务端 utf8mb4 + 客户端连接字符集 + 建库建表字符集」三个层面回答。

### 补充实测（本次安装踩到的坑，很有价值）

#### ⚠️ 坑 1：PowerShell 5.1 读 UTF-8 无 BOM 的 `.ps1` 会乱码报错
本次写脚本时反复遇到这个错误：
```
表达式或语句中包含意外的标记"$("。 字符串缺少终止符: "。
```
**原因**：Windows PowerShell 5.1 默认按系统 ANSI 代码页（中文系统是 GBK）读取**没有 BOM** 的 `.ps1` 文件。
文件里的中文和中文标点被解析成乱码字节，导致语法错误。
**解决**（三选一）：
1. 脚本里**只用 ASCII 字符**（本次最终采用的办法，最省事）；
2. 把脚本存成 **UTF-8 with BOM**：`Set-Content -Path x.ps1 -Encoding UTF8`（PWSH 5.1 的 UTF8 就是带 BOM 的）；
3. 用 **PowerShell 7（pwsh）** 执行，它默认按 UTF-8 读取。

#### ⚠️ 坑 2：`Start-Process` 在环境变量大小写重复时会直接报错
```
Start-Process : 已添加项。字典中的关键字:"NO_PROXY"所添加的关键字:"no_proxy"
```
**原因**：你的系统里同时存在 `NO_PROXY` 和 `no_proxy`（Clash 写入的），Windows 环境变量不区分大小写，
.NET 构造子进程环境字典时冲突。
**解决**：改用 `& $exe args` 直接调用，或先清掉其中一个环境变量。

#### ⚠️ 坑 3：`Get-ChildItem Env:` 在同样情况下也会报错
同类问题，枚举环境变量时会抛 `已添加了具有相同键的项`。绕开方式是用 `[Environment]::GetEnvironmentVariable()`。
